Why this exists

The answer to "where is my order" lived in three systems that didn't talk.

The ERP knows what was ordered and what the vendor promised. The freight forwarder knows what shipped and when it's due. The warehouse knows what actually landed. Nobody holds all three, so the answer gets assembled by hand, in a spreadsheet, every morning.

I built the first version of this for myself, to stop chasing shipment status across systems. It became the visibility layer other departments started running on.

The build

The status logic lives in one place, not five dashboards.

Every layer has one job. Staging only types and renames. Intermediate does the joins and the timing math. Marts decide what the business calls "late" — once — so every consumer of the data agrees on what the words mean.

raw sources → staging (4) → intermediate (2) → marts (4) → exception queue → dashboard
StatusMeaning
ON_TIMELanded on or before the estimated arrival date
IN_TRANSITMoving, not yet due
AT_RISKMoving, due within 7 days
LATEPast ETA, in transit or delivered late
NEEDS_REVIEWArrived with no warehouse receipt, or received short

The exception queue reads directly off that status. Every open item carries a plain-language reason and a priority — high-value late shipments and unreconciled receipts rise to the top. That's the model people actually open.

Data quality

Forty tests run on every build, not as a checkbox.

Generic tests cover the basics — not_null and unique on every key, relationships across the whole chain from receipt to shipment to PO to vendor, accepted values on status and mode. The custom tests are the ones that catch real operational failures.

assert_arrival_after_ship_dateA shipment can't land before it leaves — catches source date bugs and timezone handling
assert_no_negative_transit_daysGuards the calculation the on-time metric is built from
assert_receipt_not_before_arrivalCatches receipts keyed against the wrong shipment
assert_exception_queue_matches_factQueue can't drift from the fact table — nobody works a stale list
assert_on_time_rate_in_boundsPercentages outside 0–100 mean the metric broke
These aren't decorative. assert_arrival_after_ship_date caught a real bug on the first build — 25 synthetic shipments landing before they shipped, from an early-arrival offset that wasn't clamped to the transit window. The test failed, the generator got fixed. That's what the tests are for.

Run it

Clone and run. No cloud account, no credentials.

# install
pip install -r requirements.txt

# generate synthetic source data into a local DuckDB file
python scripts/generate_source_data.py

# build all models, run all 40 tests
dbt build --profiles-dir .
Done. PASS=50 WARN=0 ERROR=0 SKIP=0 TOTAL=50

# open the operations view
streamlit run app/dashboard.py

Everything downstream of staging is source-agnostic. Swapping the generator for an ERP extract means rewriting four staging models and nothing else — which is the reason the staging layer exists.
